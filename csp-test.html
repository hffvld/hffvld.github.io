Reader CSP Verification Article

By QA Test Harness · Brave iOS Reader Mode

This page exists only to exercise Brave for iOS reader mode and the way content security policy meta tags are copied into the reader document. The reader mode button appears in the browser only after the page is scored as a genuine article, and that score is driven almost entirely by how much continuous prose the page contains, so this document deliberately includes several long paragraphs of ordinary text to push the readability score comfortably over its threshold.

Readability algorithms of the Arc90 lineage walk the document looking for block level elements that hold substantial text, assign each of them a score that grows with the length of the text they contain, and then decide whether the page is worth offering in a stripped down reading view. Short pages, navigation heavy pages, and pages that are mostly links or images tend to fall below the threshold, which is exactly why an earlier version of this test page with only a placeholder line never produced a reader button on the phone.

To make the behaviour deterministic, every paragraph here is written as full sentences rather than as a few words, because the scoring function rewards longer runs of text and effectively ignores very short fragments. By stacking a handful of paragraphs of this length one after another, the cumulative score climbs well past the minimum, and the browser reliably offers reader mode on both affected and fixed builds, which is what a clean regression test needs.

Once reader mode is available, the interesting part of the test begins. The browser takes the content security policy meta tags that were present on the original page and decides which parts, if any, to carry forward into the reader document. On a build without the fix, far too much of the original policy survives, including directives that can send violation reports to a remote endpoint, and those reports can carry the privileged internal document URL along with its secret key.

On a build that contains the fix, the handling is far more conservative. Only the image source directive is adopted from each policy, and any policy that does not contain an image source directive at all is dropped completely. That single change removes the reporting directives that made the original leak possible, so a correctly fixed build should never deliver a violation report to the collector configured in the meta tags above, no matter how the policy is phrased.

The second paragraph of policy in the head of this document contains no image source directive whatsoever, which lets the tester confirm the drop behaviour directly. If any trace of that policy, or of its reporting endpoint, shows up in the reader document or arrives at the collector, the fix is not working as intended and the result should be recorded as a failure with the captured evidence attached to the report.

Finally, the image above intentionally violates an image source directive of none, which is the event that would cause a report to be generated in the first place. This gives the tester a natural trigger for the reporting path without any additional scripting, keeping the proof of concept benign and easy to reason about while still exercising exactly the code path that the security fix was written to close.

If you are reading this text inside a clean, stripped down reader view, then reader mode activated successfully and you can move on to inspecting the reader document head with Safari Web Inspector and watching the collector for any inbound violation reports. If you are still seeing the full styled page with no reader option, add more paragraphs of comparable length until the reader button appears.
